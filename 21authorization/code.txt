Authorization is the next step after authentication. It determines what an authenticated user is allowed to access or perform.

For example, in an e-commerce application:
- A normal user can view products.
- An admin can add products.
- An admin can delete products.
- A normal user cannot delete products.
Both users can log in, but they have different permissions.

1. What is Authorization?
Authorization is the process of checking whether a user has permission to access a particular resource or perform a particular action.

In simple language:
- Authentication = Who are you?
- Authorization = What are you allowed to do?
Real-life example
Imagine an office building.

Employee

Can enter the office and access their workspace.




Admin

Can enter the office and access restricted administrative areas.



The security guard first verifies the person's identity.

That is authentication.

Then the guard checks whether the person is allowed to enter a restricted room.

That is authorization.

3. What are Roles?
A role is a label assigned to a user that determines what the user is allowed to do.

For example:
Admin
User
Manager


Different roles can have different permissions.
Example of roles in an e-commerce application
Feature	Admin	Manager	User
View products	Yes	Yes	Yes
Add products	Yes	Yes	No
Update products	Yes	Yes	No
Delete products	Yes	No	No
View own orders	Yes	Yes	Yes
Manage users	Yes	No	No

Notice that different roles have different access levels.

4. What is Role-Based Access Control (RBAC)?
RBAC stands for Role-Based Access Control.

It is an authorization approach in which permissions are assigned to roles, and users are assigned those roles.

For example:
User
 |
 |---- Role: Admin
 |         |
 |         |---- Add Product
 |         |---- Delete Product
 |         |---- Manage Users
 |
 |---- Role: Normal User
           |
           |---- View Product
           |---- Buy Product


Instead of checking individual permissions for every user, the application checks their role.
How does RBAC work?
Suppose a user logs in and their database record contains:
{
    "name": "Akshat",
    "email": "akshat@gmail.com",
    "role": "admin"
}


The backend knows that this user has the admin role.

When the user requests an admin-only API, the backend checks:
if (user.role === "admin") {
    // Allow access
}


If the user is not an admin, access is denied.

6. Important HTTP Status Codes
Two status codes are particularly important here.
Status	Meaning	Example
401	Unauthorized – authentication is missing or invalid	No valid JWT
403	Forbidden – identity is known, but permission is insufficient	Normal user accessing admin API

Remember:
- 401 = You haven't successfully authenticated.
- 403 = You are authenticated, but you don't have permission.

9. What is Permission-Based Authorization?
So far, we have checked roles.

But sometimes applications need more detailed permissions.

For example:
Admin:
- create_product
- update_product
- delete_product
- manage_users

Manager:
- create_product
- update_product

User:
- view_product
- buy_product


This is more flexible than checking only roles.

For example, instead of checking:
allowRoles("admin")


We could check:
allowPermissions("delete_product")


This approach is useful when applications have many roles and complex access rules.

RBAC and permission-based checks can also be combined.

10. What is Resource-Based Authorization?
Resource-based authorization checks whether a user is allowed to access a particular resource.

Example:

Suppose two users have accounts:
User A → Account 101
User B → Account 102


User A should not be able to access User B's private account just by changing an ID in the URL.

For example:
GET /api/accounts/102


The backend must check whether the authenticated user owns account 102 or has an authorized role.

This is different from simply checking whether someone is logged in.

It is especially important for:
- Orders
- User profiles
- Private documents
- Bank accounts
- Real estate listings
- Invoices

11. Important Security Best Practices
1. Never allow users to assign themselves admin roles through public registration.
2. Verify JWT signatures before checking roles.
3. Don't trust role information directly from the request body.
4. Check resource ownership when accessing private resources.
5. Use HTTPS.
6. Keep JWT secrets private.
7. Consider current database roles for sensitive operations.
8. Return 401 for failed authentication and 403 for insufficient permission.
9. Log sensitive administrative actions.
10. Apply the principle of least privilege: give each user only the permissions they need.

13. Interview Questions
Q1. What is authorization?

Authorization determines what an authenticated user is allowed to access or perform.

Q2. What is RBAC?

Role-Based Access Control assigns permissions to roles and roles to users.

Q3. What is the difference between 401 and 403?

401 means authentication is missing or invalid. 403 means the user is authenticated but does not have sufficient permission.

Q4. What is authorization middleware?

It is Express middleware that checks the user's role or permission before allowing access to a route.

Q5. Why should users not select their own roles during registration?

Because they could assign themselves privileged roles such as admin.

Q6. Can a normal user access an admin route?

Not if the backend correctly checks authorization.

Q7. What is the principle of least privilege?

Give users only the permissions they need to perform their tasks.

Q8. What is resource-based authorization?

It checks whether the user has permission to access a particular resource, such as their own order or account.

Q9. Is authentication enough to protect an admin route?

No. Authentication verifies identity, but authorization must also verify the user's permissions.

Q10. Should we trust the role sent by the frontend?

No. The backend must determine the user's role from a trusted source.
