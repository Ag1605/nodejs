In the previous lesson, we learned about Cookies. Now let's understand Sessions.

Sessions are very important in backend development because they help a server remember users across multiple requests.

By the end of this lesson, you will understand sessions completely and build a working session-based login and logout system using Express.js.

1. What is a Session?
A session is a way to store information about a user on the server across multiple HTTP requests.

For example:
1. You log in to Instagram.
2. Instagram remembers that you are logged in.
3. You open your profile.
4. You open your messages.
5. You move to another page.
You don't need to log in again on every page.

How does the server remember you?

It uses a session.
Why do we need sessions?
First, understand one important concept: HTTP is stateless.

Stateless means every HTTP request is independent.

For example:
Request 1: Login
Request 2: Open Profile
Request 3: Open Dashboard


The server does not automatically remember that Request 1 was a successful login when Request 2 arrives.

Sessions solve this problem by allowing the server to remember information about a user.

2. Cookie vs Session
This is the most important difference to understand.
Cookie

Stored in the browser

The browser stores cookie data and sends it with matching requests.



Session

Stored on the server

The server stores user-related session data in a session store.



Let's understand with an example.

Suppose you log in to a website.

The server stores:
{
    userId: 101,
    username: "Akshat",
    email: "akshat@gmail.com"
}


This information is stored in a server-side session.

But how will the server identify which session belongs to your browser?

It uses a Session ID.

The browser receives a cookie containing something like:
sid = abc123xyz789


This ID identifies your session. The actual user information remains on the server.

Remember:
- Cookie = Stored in browser.
- Session data = Stored on server.
- Session ID = Connects the browser to its session.

3. How does Session Management work internally?
Let's understand the complete flow.
Session working flow
1. Browser

User enters email and password

POST /login

2. Express Server

Checks the login credentials

Creates session data

3. Session Store

Stores user information against a session ID

Server sends session ID cookie

4. Browser

Stores the session ID cookie


When the user makes another request:
Browser sends the session ID cookie

Server finds the session in the session store

Server identifies the logged-in user and allows access

Step-by-step explanation
Step 1: User sends login credentials.
{
    "email": "akshat@gmail.com",
    "password": "123456"
}


Step 2: Server checks whether the credentials are correct.

Step 3: Server creates a session and stores user information.

Step 4: Server sends a session ID to the browser through a cookie.

Step 5: Browser automatically sends that cookie with subsequent matching requests.

Step 6: Server uses the session ID to find the user's session.

Step 7: Server allows the user to access protected routes.

4. Important Session Terminology
Term	Meaning
Session	Server-side user information
Session ID	Unique identifier for a session
Session Store	Place where session data is stored
Session Cookie	Cookie containing the session ID
Session Expiry	Time after which a session expires
Session Regeneration	Creating a new session ID
Session Destruction	Removing a session

What is a Session Store?
A session store is where the server stores session information.

For example:
Session ID: abc123

Session Data:
{
    userId: 101,
    username: "Akshat"
}


Common session stores:
- MemoryStore – stores sessions in server memory.
- Redis – commonly used for production session storage.
- MongoDB – can store sessions using a compatible session-store package.
The default MemoryStore provided by express-session is for development, not production.

5. What is express-session?
Express does not provide session management by default.

We use a third-party package called:

express-session

It helps us:
- Create sessions.
- Store session data.
- Read session data.
- Update session data.
- Destroy sessions.
- Manage session cookies.
Install it:
npm install express-session


Import it:
const session = require("express-session");


Configure it:
app.use(session({
    secret: "my-secret-key",
    resave: false,
    saveUninitialized: false
}));


Let's understand these properties.
Property	Meaning
secret	Secret used to sign the session ID cookie
resave	Avoids saving an unchanged session unnecessarily
saveUninitialized	Avoids saving new sessions that have not been modified

The secret should be a long, random value stored in environment variables, not directly in your source code.

15. What is Session Fixation?
Session fixation is a security attack.

Imagine:
1. An attacker gets a session ID.
2. The attacker tricks a user into using that same session ID.
3. The user logs in.
4. If the session ID is not changed, the attacker might reuse it to access the user's session.
To reduce this risk, regenerate the session ID after successful login:
req.session.regenerate((err) => {
    if (err) {
        return next(err);
    }

    req.session.user = {
        id: demoUser.id
    };
});


This is why we used req.session.regenerate() in our login API.

16. Where should sessions be stored in production?
In our project, we used the default MemoryStore.

It is fine for learning and local development, but it is not suitable for production.

Why?

Suppose your server restarts.

The sessions stored in its memory are lost.

Also, if you run multiple server instances, they won't automatically share the same memory.

For production, use an external session store.
Session store	Purpose
MemoryStore	Local development
Redis	Fast, common production choice
MongoDB	Persistent session storage

Popular packages include connect-redis and connect-mongo.

17. Session Security Best Practices
1. Always use HTTPS in production.
2. Set httpOnly: true.
3. Use secure: true with HTTPS.
4. Use a strong session secret stored in .env.
5. Regenerate the session ID after login.
6. Destroy sessions during logout.
7. Set an appropriate session expiry.
8. Use a production-ready session store.
9. Implement CSRF protection where required.

18. Cookie vs Session – Interview Comparison
Cookie	Session
Stored in browser	Data stored on server
Can store small pieces of data	Can store user-related session data
Browser sends it with matching requests	Session ID cookie identifies the session
Can have an expiry	Session has a lifecycle and expiry
Can be read by JavaScript unless protected	Session data isn't directly stored in browser

Important: A session often uses a cookie. They are not competing technologies.

19. Interview Questions
Q1. What is a session?

A session is a way to store user-related information on the server across multiple HTTP requests.

Q2. Why do we need sessions?

Because HTTP is stateless. Sessions help the server remember users between requests.

Q3. Where is session data stored?

In a session store, such as MemoryStore, Redis, or MongoDB.

Q4. What is a session ID?

A unique identifier used to find a particular user's session.

Q5. What is express-session?

It is an Express.js middleware package used to manage sessions.

Q6. What is req.session.destroy()?

It destroys the current session.

Q7. What is req.session.regenerate()?

It creates a new session ID, which is useful for preventing session fixation.

Q8. Why is MemoryStore not recommended for production?

It is not designed for production use, does not share sessions across server instances, and can cause memory-related problems.

Q9. Can sessions work without cookies?

Yes, alternative ways of sending session identifiers exist, but cookies are the common approach for browser-based applications.

Q10. What is the difference between a cookie and a session?

A cookie is stored in the browser, whereas session data is stored on the server. The browser commonly stores only the session ID.
